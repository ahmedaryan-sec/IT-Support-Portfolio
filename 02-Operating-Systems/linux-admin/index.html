A desk reference for Linux tickets.

This is a working reference for Tier 1 and Tier 2 technicians who already have a ticket open. It covers the filesystem locations you will be asked about, nine common failure patterns with a checklist for each, and the syntax for the commands you reach for while diagnosing.

Work in this order: look up a path you do not recognise, open the playbook that matches the symptom, then confirm the command before you run it. A playbook is a starting point, not a diagnosis.

Before you type

  • Confirm the host, the affected user, and whether it is production.
  • Read the exact error text. The last line is often the least useful.
  • Check you have authority to change the host, and know how to undo it.
  • Adapt every example to your environment and your organization's policy.

    Layouts differ between distributions

    On most current distributions /bin, /sbin, and /lib are symlinks into /usr (the "merged /usr" setup). Debian and Ubuntu moved to this by default in recent releases, Fedora and Arch moved earlier. Check with ls -ld /bin /sbin /lib instead of assuming either layout.

    /root is not /

    /root is the home directory of the root user, normally mode 0700. / is the root of the filesystem tree. Commands that work on one say nothing about the other.

    Sources and limits

    Checked November 2026

    Documentation used

    • Filesystem Hierarchy Standard 3.0 (directory purposes, merged-/usr notes).
    • proc(5) (/proc and process-file behaviour).
    • journalctl(1) and systemctl(1) (log and service inspection).
    • crontab(5), cron(8), crontab(1) (scheduling fields, environment, % escaping).
    • GNU Coreutils manual (df, du, cp, mv, ls).
    • rsync(1), lsof(8), ss(8), ip(8) (copy, open files, sockets, addresses).
    • apt(8) (Debian) and DNF command reference (RHEL family).
    • Ubuntu Server documentation and Fedora DNF quick docs.

    What this page cannot tell you

    • Your distribution's exact defaults. Read /etc/os-release and the vendor docs for the version in front of you.
    • Where your logs and authentication records go. Logging is configured per host and may be shipped to a central system.
    • Whether a fix is approved. Change control, data handling, and incident response come from your organization.

    Red Hat's product documentation was not reachable from the build environment, so the RHEL-family notes here rest on the DNF reference and upstream manual pages rather than on Red Hat pages themselves.

    Examples only. Check the host, the version, and your policy before running anything that changes state.
